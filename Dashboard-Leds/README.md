# Dashboard de Leads RED

Dashboard comercial construido con React, JavaScript/JSX, Vite y Tailwind CSS.

## Desarrollo local

1. Copia `.env.example` a `.env.local` y define `RED_API_KEY` en ese archivo. No publiques la clave ni uses un prefijo `VITE_`.
2. Ejecuta `npm install` y después `npm run dev`.
3. Ejecuta `npm run lint` y `npm run build` para validar el proyecto.

Durante el desarrollo, Vite actúa como proxy de `/api/metrics/reuniones` hacia `https://prospektia.red.com.sv` e inyecta `X-API-KEY` desde el entorno del servidor. En Vercel, `api/metrics/reuniones.js` implementa la misma ruta como una función serverless y lee `RED_API_KEY` del entorno. El navegador llama al endpoint de mismo origen; la credencial no se compila en el bundle.

Los leads se vuelven a consultar cada cinco minutos mientras el dashboard está abierto y visible, y al regresar a la pestaña si los datos ya tienen cinco minutos o más. Las solicitudes del navegador usan `cache: 'no-store'`; el botón **Actualizar** sigue disponible para una recarga manual. La marca “Actualizado” representa la última carga completa exitosa de todas las páginas.

## Despliegue en Vercel

1. Importa el repositorio en Vercel y configura `Dashboard-Leds` como **Root Directory**.
2. Usa `npm run build` como **Build Command** y `dist` como **Output Directory**.
3. Añade `RED_API_KEY` en **Project Settings → Environment Variables** para los entornos donde se desplegará. No uses el prefijo `VITE_`.
4. Despliega o vuelve a desplegar el proyecto después de guardar la variable.

## Datos y reglas

La API real devuelve `{ items, total, limite, ... }`. En la auditoría, `total` corresponde al tamaño de la página, no al total global; el servicio por eso solicita offsets `0, 50, 100, ...` hasta recibir una página menor a 50. Los conteos cambian con la actividad del API: validar siempre la carga actual, no asumir que un total anterior es constante. `id` es el identificador interno del registro y `client_id` es el ID comercial visible (por ejemplo, `LD…`); se conserva el primero para claves y overrides y se muestra el segundo en las vistas. `client_id` puede repetirse entre países, por lo que no debe usarse solo para eliminar duplicados. El estado del flujo (`status`) es la autoridad de abierto/cerrado: `cerrado/perdida` se mapea a perdido, `cerrado/cerrada` a ganado, `en_proceso` a activo, `no_agendado` a en espera y `stage_2_overdue` a detenido; un cerrado sin resultado se cuenta como inválido. Un resultado de pérdida en un registro todavía `en_proceso` se conserva como abierto y se informa como conflicto, no se cuenta simultáneamente como cierre perdido.

Los filtros de ejecutivo, país y mes producen `resumenBase()`. El filtro mensual usa únicamente una fecha real de próxima gestión; no sustituye la fecha de reunión. Esta puede venir en `start_time` o, si falta, en `stage_feedback_json.2.fecha_reunion`; el comentario de reunión se lee únicamente desde `retroalimentacion` o `notes` de esa etapa. Las fechas de solo día se validan como fechas de calendario y se guardan sin zona horaria para evitar desplazarlas al mostrarlas. En la consulta auditada el 13 de octubre de 2026, `start_time` estaba informado en 173/1,331 filas; la fecha de etapa 2 en 901, de las cuales 900 eran válidas y una se descartó por formato/valor no reconocido. La etapa 5 además ofrece `fecha_seguimiento`: en esa misma consulta estaba en 198 filas, incluyendo 72 de 76 leads abiertos en esa etapa; las 72 fechas reportadas eran anteriores al 13 de octubre. Se presenta con la etiqueta “seguimiento reportado”, no como fecha futura ni cierre estimado. Las cifras dependen del estado del API y no se fijan en el dashboard. Algunas próximas gestiones aparecen dentro de `stage_feedback_json.<etapa>.proxima_gestion`, con `fecha_hora` y `notas`; la cobertura es parcial y la gestión más recientemente creada se usa como la vigente. En Resumen, el bloque desplegable de seguimiento vencido identifica cliente, ID, estado, etapa, fecha, días de atraso y comentario de cada gestión vencida. Los leads abiertos sin próxima gestión se presentan aparte: no se consideran vencidos porque no hay fecha reportada con la cual comprobar el atraso. La API no incluye fecha estimada de cierre, inclusión a forecast o historial de etapas; no se infieren desde otros campos. En particular, `stage_2_overdue` por sí solo no prueba que exista una fecha vencida. La etapa API 5 es `SEGUIMIENTO`; no hay una etapa específica de documentación.

El Directorio es un módulo independiente del Resumen y muestra los datos comerciales disponibles, incluidos los comentarios de próxima gestión y reunión por separado. La API consultada no incluye el campo `calificado`, por lo que ese indicador no se presenta en el Directorio. El bloque “Leads en proceso” del Resumen conserva la distribución por etapa actual del API; el embudo acumulado se muestra únicamente en Pipeline. Resultados ofrece conteo de cierres, conversión (`ganados / (ganados + perdidos)`) y motivos basados primero en `stage_feedback_json.6.razon_cierre` (prefijo de catálogo antes de `:`) y después en `stage_feedback_json.6.motivo_no_contacto`. No se usa `categoria_cierre` para homologar motivos porque la auditoría encontró allí rubros/productos además de motivos. Los valores no reconocidos quedan en “Otros / revisar” y se despliegan desde el campo de motivo; las pérdidas sin datos en esos campos quedan como “Sin categoría informativa”. “Radios reportadas en leads ganados” suma menciones explícitas de radios en comentarios; no es un campo estructurado de ventas ni confirma unidades vendidas. En Forecast, la cantidad estructurada usa `stage_feedback_json.<etapa>.cantidad_equipos`, `equipos` o `cantidad_oferta` y se mantiene separada de una mención numérica en comentarios de la etapa actual. No se reutilizan comentarios históricos para completar el dato, ni se suman ambas fuentes; la tabla identifica la fuente por fila. Estas cantidades no equivalen a radios vendidas, por lo que los totales de Forecast y Resultados tienen alcances distintos. Los leads sin evidencia se muestran como “Sin dato”, no se interpretan como cero. La selección automática de Forecast requiere etapa API 5 (`SEGUIMIENTO`) y cualquier estado abierto; se permiten inclusiones manuales para otras oportunidades abiertas, pero se excluyen resultados de venta contradictorios. La fecha estimada de cierre y las inclusiones/exclusiones manuales se guardan en localStorage de ese navegador. Los comentarios se muestran abreviados y se pueden abrir completos. La API entrega fechas de reunión, seguimiento y cierres reales, pero no fecha estimada de cierre; ninguna fecha de gestión se reutiliza como pronóstico. El embudo visual de Pipeline se estima desde la etapa actual y no equivale a un historial de transiciones; al desplegar la etapa Cierre, los leads quedan agrupados por estado. `calculateMetrics()` valida también la partición de estados en los datos globales y filtrados.
