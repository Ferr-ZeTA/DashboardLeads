# Dashboard de Leads RED

Dashboard comercial construido con React, JavaScript/JSX, Vite y Tailwind CSS.

## Desarrollo local

1. Copia `.env.example` a `.env.local` y define `RED_API_KEY` en ese archivo. No publiques la clave ni uses un prefijo `VITE_`.
2. Ejecuta `npm install` y después `npm run dev`.
3. Ejecuta `npm run lint` y `npm run build` para validar el proyecto.

Durante el desarrollo, Vite actúa como proxy de `/api/metrics/reuniones` hacia `https://prospektia.red.com.sv` e inyecta `X-API-KEY` desde el entorno del servidor. En Vercel, `api/metrics/reuniones.js` implementa la misma ruta como una función serverless y lee `RED_API_KEY` del entorno. El navegador llama al endpoint de mismo origen; la credencial no se compila en el bundle.

## Despliegue en Vercel

1. Importa el repositorio en Vercel y configura `Dashboard-Leds` como **Root Directory**.
2. Usa `npm run build` como **Build Command** y `dist` como **Output Directory**.
3. Añade `RED_API_KEY` en **Project Settings → Environment Variables** para los entornos donde se desplegará. No uses el prefijo `VITE_`.
4. Despliega o vuelve a desplegar el proyecto después de guardar la variable.

## Datos y reglas

La API real devuelve `{ items, total, limite, ... }`. En la auditoría, `total` corresponde al tamaño de la página, no al total global; el servicio por eso solicita offsets `0, 50, 100, ...` hasta recibir una página menor a 50. Los conteos cambian con la actividad del API: validar siempre la carga actual, no asumir que un total anterior es constante. La identidad de reunión es `id`; `client_id` se puede repetir entre países, por lo que no debe usarse solo para eliminar duplicados. El estado del flujo (`status`) es la autoridad de abierto/cerrado: `cerrado/perdida` se mapea a perdido, `cerrado/cerrada` a ganado, `en_proceso` a activo, `no_agendado` a en espera y `stage_2_overdue` a detenido; un cerrado sin resultado se cuenta como inválido. Un resultado de pérdida en un registro todavía `en_proceso` se conserva como abierto y se informa como conflicto, no se cuenta simultáneamente como cierre perdido.

Los filtros de ejecutivo, país y mes producen `resumenBase()`. El filtro mensual usa únicamente una fecha real de próxima gestión; no sustituye la fecha de reunión. Esta puede venir en `start_time` o, si falta, en `stage_feedback_json.2.fecha_reunion`; el comentario de reunión se lee únicamente desde `retroalimentacion` o `notes` de esa etapa. Las fechas de solo día se validan como fechas de calendario y se guardan sin zona horaria para evitar desplazarlas al mostrarlas. En la consulta auditada el 13 de octubre de 2026, `start_time` estaba informado en 173/1,331 filas; la fecha de etapa 2 en 901, de las cuales 900 eran válidas y una se descartó por formato/valor no reconocido. La etapa 5 además ofrece `fecha_seguimiento`: en esa misma consulta estaba en 198 filas, incluyendo 72 de 76 leads abiertos en esa etapa; las 72 fechas reportadas eran anteriores al 13 de octubre. Se presenta con la etiqueta “seguimiento reportado”, no como fecha futura ni cierre estimado. Las cifras dependen del estado del API y no se fijan en el dashboard. Algunas próximas gestiones aparecen dentro de `stage_feedback_json.<etapa>.proxima_gestion`, con `fecha_hora` y `notas`; la cobertura es parcial y la gestión más recientemente creada se usa como la vigente. Las fechas de vencimiento se calculan solo desde esa fecha programada. La API no incluye fecha estimada de cierre, inclusión a forecast o historial de etapas; no se infieren desde otros campos. En particular, `stage_2_overdue` por sí solo no prueba que exista una fecha vencida. La etapa API 5 es `SEGUIMIENTO`; no hay una etapa específica de documentación.

Los registros originales se conservan en memoria y están disponibles mediante la expansión de cada fila del directorio, dentro de Resumen. El directorio separa el comentario de próxima gestión del comentario de reunión y conserva los campos originales para consulta. Resultados ofrece un conteo de cierres, conversión (`ganados / (ganados + perdidos)`), categorías homologadas desde el texto libre `categoria_cierre` y un conteo conservador de radios mencionadas explícitamente en comentarios de leads ganados. La categoría “Otros / revisar” se puede desplegar para ver los textos originales y sus leads. Para evitar repetir una misma oportunidad se toma la mayor cantidad reconocida por lead; los cierres sin cantidad explícita no se interpretan como cero. El Forecast automático se limita a leads abiertos en etapa API de cierre o con mención explícita de firma pendiente en comentarios de su etapa actual; no basta estar en seguimiento. La cantidad de equipos se lee primero desde `stage_feedback_json.<etapa>.cantidad_equipos` (y otros campos estructurados de cantidad); si no existe, se busca una cantidad explícita asociada a radios/equipos en el comentario. Si no hay evidencia de cantidad, se muestra “Sin dato”. La tabla permite administrar inclusión y fecha estimada de cierre manual; los comentarios se muestran abreviados y se pueden abrir completos. La API entrega fechas de reunión, envío de propuesta, seguimiento y cierres reales; ninguna de ellas equivale a una fecha estimada de cierre. Los overrides se guardan en localStorage de ese navegador. Los registros con resultado cerrado contradictorio quedan excluidos. La fecha manual estimada nunca se confunde con la próxima gestión ni con la fecha de reunión. El embudo visual se estima desde la etapa actual y no equivale a un historial de transiciones. `calculateMetrics()` valida también la partición de estados en los datos globales y filtrados.
